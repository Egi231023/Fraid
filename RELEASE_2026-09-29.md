# Fraid: readiness fixes for 5 October 2026

This release fixes five reproduced production defects:

- A reviewed attendance entry clears its stale-review flag only after an administrator confirms valid times, directly or through an approved correction. The audit preserves the original values. Overlapping entries remain excluded from verified hours.
- Only one correction may be pending for an entry. Employees can withdraw their own request; administrators can reject it with a reason. Approval or a completed direct repair supersedes other pending requests with an audit trail. Existing stale requests remain rejectable.
- The planner calculates staffing for every time interval. An 08:00–12:00 shift no longer satisfies an 08:00–16:00 opening window. Suggestions use entered availability; uncovered intervals are shown explicitly.
- Wage changes require an effective date and reason. Payroll uses the rate applicable on each worked day. Existing undated rates are preserved, but historical payroll remains incomplete until an administrator confirms actual validity. An explicit same-date correction requires a separate checkbox and is audited.
- Scheduled payroll catches up after a missed day/month, using existing delivery reservations. Automatic catch-up starts with September 2026 payroll, first due 15 October, to avoid unsolicited historic backfill. At most one new report is attempted per run. Uncertain SMTP deliveries remain protected against automatic resending.

## Validation

Run `npm ci --ignore-scripts`, `npm run check`, and `npm test`. Tests use synthetic isolated databases, including role restrictions, review flags, pending-request resolution, idempotency, historical and mid-month rates, interval staffing, scheduler dates, and real form submission through the database RPC. Frontend and Edge report calculations match. The Edge entrypoint was bundled successfully as a syntax/import check.

A private snapshot of the nine relevant Fraid operational/scheduler tables, metadata, function definitions and Edge source was restored into an isolated PGlite instance. Row values, indexes, function definitions and execution ACLs matched. The new migration and its function rollback were exercised there. Auth credentials, Vault secrets, Storage and unrelated Biogreens data are not part of this drill. The private archive must never be committed to this public repository.

Existing transactional database and deferred-registration suites should also be run on an isolated restored snapshot, never by adding fake payroll or attendance to production.

## Deployment and recovery

1. Preserve the private operational snapshot. Confirm the live function matches the migration precondition.
2. Apply `supabase/migrations/20260929122858_monday_readiness.sql`. It changes only the existing write function, preserving permissions and operational rows.
3. Deploy `fraid-scheduled-reports` with its sibling source files and `verify_jwt=false`, retaining its existing internal job-token authorization and environment secrets.
4. Publish the frontend from the matching Git commit. Existing tabs must refresh before editing wages.
5. Verify live source versions, anonymous RPC denial and scheduler health without sending test messages.

The migration refuses an unexpected live function revision. `db/write-record.sql` is the resulting canonical definition. `db/rollback-monday-readiness.sql` restores the old function without rewriting operational data. Do not blindly roll the complete release back after dated wage history has been entered: the old frontend/reporting code does not understand that history. Prefer a forward fix; if emergency rollback is necessary, pause wage editing and automatic payroll, preserve all new records and audit history, and reconcile the rate-aware calculation before resuming.

## Administrator setup still required

In Administrácia → Príprava prevádzky:

- Confirm actual opening hours and capacity.
- Confirm each person's actual wage and effective date, including historic dates needed for reports.
- Link the remaining verified employee account to the existing profile; do not create a duplicate profile.
- Enter actual stock and approved opening/closing tasks.
- Resolve the open historical attendance entry using the actual departure time.

Notification permission is per device. Physical phone testing and receipt of push messages have not been claimed. AI remains explicitly disabled; it is not required for attendance, scheduling or daily closing. No invented employee, wage, attendance, stock or sales data is written by this release.
